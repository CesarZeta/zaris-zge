`browser_type` y `browser_eval` con `Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set.call(el, val)` cambian el DOM pero **React no se entera del cambio** (el state interno queda con el valor anterior, y al submit envía el valor viejo o vacío).

**Why:** React 18 con events sintéticos no detecta confiablemente `input`/`change` disparados así desde código externo cuando el componente es de un bundle de prod (no HMR). Es el mismo patrón que `feedback_dnd_sintetico_no_funciona` para @dnd-kit.

**How to apply:**
- Para tests E2E del flujo del usuario final (form público de autoservicio, login, búsquedas con click) → **sí funciona** con `browser_type` porque el evento es trusted.
- Para setup de datos (crear evento test, cargar maestros, montar precondiciones) en módulos React → **NO usar browser**. Llamar a la API directamente con `curl`/`fetch` y luego volver al browser para validar el flujo del usuario.
- Caso real 2026-05-12 E2E autoservicio prod: intenté crear el evento test via browser_type en EventoModal (vanilla shell + iframe React). El form aceptaba inputs pero submit cerraba el modal sin crear nada porque el state interno seguía vacío. Pasé a `POST /api/v1/agenda/eventos` con curl + JWT y funcionó al primer intento.

**Sub-quirk relacionado:** después de cerrar un modal o navegar al mismo hash, **React no remonta** el componente. El state queda con valores tipeados previos concatenados (caso real: DNI quedó "776655443344556622334455" después de 3 intentos de submit). Workaround: `location.reload()` entre intentos en lugar de re-navegar al mismo hash.

**Matiz importante (sesión 2026-05-27, dev server `localhost:5173`):** en **dev mode (Vite HMR)** el setter nativo `Object.getOwnPropertyDescriptor(...).set.call(el, val)` + `dispatchEvent(new Event('input',{bubbles:true}))` **SÍ dispara el onChange de React de forma confiable** — lo usé para limpiar inputs, llenar filas de opciones y elegir un `<select>` (setter sobre `HTMLSelectElement.prototype` + `change`), todo reaccionó. Lo que NO funciona confiable es el **bundle de prod en iframe** (el caso original de esta memoria). Regla afinada: si estás iterando un módulo React en el **dev server standalone**, el setter sintético es válido para tests; reservá "setup via API" para cuando pruebes el **bundle de prod** o el shell vanilla+iframe. `browser_type` (evento trusted) funciona en ambos pero **appendea** al valor existente, no reemplaza.

**Patrón de sesión para entrar a un módulo protegido en `localhost:5173` (sesión 2026-05-27):** tras `browser_navigate` a una URL con hash, la app suele quedar en `#/login` aunque el localStorage tenga sesión válida — el store zustand (`useAuthStore`) ya se inicializó vacío en ese tab y el router quedó en login. Secuencia que funciona: (1) `browser_navigate` a `localhost:5173/` raíz; (2) `browser_eval` que escribe `zaris_session` con el **dual-shape** (`{state:{accessToken,user},version:0, access_token, user}`, §29) usando un token fresco de `/auth/login`; (3) `browser_navigate` de nuevo al `/#/ruta` (recarga → zustand-persist hidrata al boot); (4) si AÚN quedó en `#/login`, navegar **por `location.hash`** dentro de la SPA (no `browser_navigate`) — ahí entra. El token JWT scope agente dura ~24h: si reusás una sesión de la víspera, verificá el `exp` (`new Date(exp*1000)`) antes de culpar a la inyección.

**Contra-ejemplo (sesión 2026-05-28, dev server, `DisponibilidadView` feriados):** acá NI `setVal` sintético NI `browser_type` dispararon el onChange — el form mostraba los valores en el DOM pero al click en "Agregar" el state de React iba vacío y el POST nunca salió (verificado: la fila no aparecía en DB). O sea: el "matiz 2026-05-27 (setter funciona en dev)" **NO es universal** — depende del componente. **Regla final, sin vueltas: para verificar que un alta por form funciona, NO pelees con inputs sintéticos. Hacé el POST por API (idéntico a lo que llama el hook del form) + `location.reload()` + confirmá que la tabla del form lo renderiza.** Eso cierra el ciclo render→API→tabla, que es lo verificable de forma fiable. "El botón llama al hook" ya lo garantiza el código.

**Swap de ROL/sesión también exige reload (sesión 2026-05-28):** al cambiar de usuario reescribiendo `zaris_session` por `browser_eval` (ej. de admin a operador para probar scoping/gating), el store `useAuthStore` en memoria **sigue con el user viejo** hasta un `location.reload()` real. Síntoma que casi reporté como bug: el tab "Prestaciones" (gated a `hasPermission(2)`) seguía visible tras loguear como nivel 3 — era el admin cacheado, no un fallo de gating. Tras `location.reload()` el tab desapareció correcto. **Regla: para verificar permisos/gating por rol, swap de sesión + `location.reload()`, nunca solo navegar al hash.** Verificá `JSON.parse(localStorage.zaris_session).state.user.nivel_acceso` Y que el render ya refleje ese nivel antes de juzgar.

**PELIGRO — `browser_click` con selector genérico `button` deslogueó (misma sesión):** `browser_click({selector:'button'})` cliquea el PRIMER `<button>` del DOM, que en el shell suele ser un nav/logout → me limpió `zaris_session` y mandó a `#/login`, perdiendo el contexto del test. **Nunca cliquear `button` a secas.** Para cliquear por texto usar `browser_eval` con `[...document.querySelectorAll('button')].find(b=>b.textContent.trim()==='Agregar').click()`.

**Un `alert()`/`confirm()` nativo de la app CONGELA el CDP del browser MCP (sesión 2026-06-01):** mientras un diálogo nativo del navegador está abierto, TODO `browser_eval`/`Runtime.evaluate` da `CDP request timed out after 30000ms` — incluso en el top frame. `browser_navigate` NO lo descarta. `browser_status` lo delata con `Page.javascriptDialogOpening: 1` en el contador de eventos. Solución: pedirle al usuario que lo cierre a mano (toca "Aceptar"), o `browser_navigate('about:blank')` que a veces lo libera. **Prevención: cliquear por texto EXACTO** (`b.textContent.trim()==='Nuevo'`, no `/Nuevo/`) para no disparar por accidente un botón que abre un diálogo — caso real: buscando "Nuevo" cliqueé "Nuevo borrador" del builder de trámites, que hace `alert("Nueva versión v3 creada")` y colgó el bridge varios turnos.

**Matiz 2026-06-11 (QA Emergencias en PROD, bundle en iframe del shell vanilla):** el setter nativo (`Object.getOwnPropertyDescriptor(<proto>, 'value').set.call(el, v)` + `dispatchEvent(new Event('input'|{change para selects}, {bubbles:true}))`) funcionó **consistentemente** en ~15 interacciones del módulo Emergencias (inputs, selects con `HTMLSelectElement.prototype`, textareas con `HTMLTextAreaElement.prototype`, radios con `.click()`): los POST salieron con los valores correctos, verificado por los eventos creados. Refuerza el "depende del componente": inputs controlados simples reaccionan bien incluso en prod. **Regla práctica: intentar el setter nativo PRIMERO verificando su efecto inmediato** (¿se habilitó el botón? ¿apareció el dropdown?) y caer a setup-por-API solo si el componente no reacciona. Y en PROD, esperar 5-6s tras cada mutación antes de juzgar (latencia Railway↔Supabase ~2-3s; 3 checks prematuros dieron falsos negativos esta sesión).

**Trampa del selector ancestro (2026-06-10, costó 2 mutaciones erradas):** `[...querySelectorAll('div')].find(d => d.textContent.includes('EM-...-000010'))` devuelve el PRIMER div en orden de documento que contiene el texto = el **contenedor exterior de toda la lista**, no la card — y `card.querySelector('button')` agarró el botón de OTRA card (cerró el evento equivocado; el FSM backend lo rechazó con 422 y salvó el dato). **Fix: localizar el elemento HOJA con texto exacto (el botón del nro) y subir con `.closest()`**, nunca find sobre divs por `.includes()`.
